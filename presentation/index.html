📷 IG Feed Watcher

A headless, cron-driven pipeline that watches an Instagram feed, classifies new posts into interest groups, alerts a Telegram channel per group, runs custom hooks — and can even post images back to Instagram. Everything it sees is stored in SQLite and explored through a web dashboard.

What the system does

Three independent services share one session and one database — a watcher, a posting API and an explorer dashboard.

Cron scheduler · every 5 min→ Headless Chromium opens instagram.com→ Feed scraped → new posts detected→ Group matching→ SQLite + screenshot + hook→ Telegram topics
Watch

📡 Feed watcher

watcher.js launches a stealth-flagged Chromium with your cookies.json session, scrolls the feed, parses every <article> (author, caption, timestamp, image URLs, reel/photo), and keeps a seen-set (state.json + DB) so nothing is processed twice. Capped at 10 new posts per run.

Alert & act

🔔 Classification → Telegram

Every new post is matched against interest groups (accounts, keywords, hashtags in groups.json). Matched posts are sent as photo + caption to the group's own Telegram forum topic; the rest go to the main channel. A custom bash hook (hooks/on-new-post.sh) receives the full post JSON on stdin for any extra logic.

Publish & explore

📤 Posting API + Explorer

post-server.js exposes POST /post to publish an image back to Instagram through the same session. server.js is a dark-themed web dashboard that browses, filters and searches everything in posts.db, with per-post comments and manual group assignment.

One session, three consumers: the watcher, the poster and the API server all read the same cookies.json; the watcher and the explorer share the same SQLite file posts.db (bind-mounted into the explorer's Docker container).

🔄 Workflow diagram — trigger → scrape → detect → enrich → alert (scroll inside the frame) Open full size ↗

🧩 Step by step

  • 1 · Prepare — init SQLite schema, load the seen-set (state.json ∪ DB shortcodes), load groups, ensure each group has a Telegram forum topic.
  • 2 · Connect — launch Chromium (stealth UA, automation flags off), set cookies, open instagram.com with 2 retries, dismiss “Not now” popups, abort fonts/media for speed.
  • 3 · Scrape — scroll the feed 3× and parse <article> blocks into post objects.
  • 4 · Detect — filter out seen shortcodes; sort matched posts first; cap at 10 per run.

🧩 Step by step (cont.)

  • 5 · Enrich — capture the post image (or screenshot the article); open the detail page for matched / likely-truncated posts to get the full caption and comments.
  • 6 · Persist — INSERT the post + comments into posts.db.
  • 7 · Alert — run on-new-post.sh with JSON on stdin, then send a Telegram sendPhoto to each matched group's topic (or the main channel).
  • 8 · Close — mark everything seen, save state.json, persist the rate-limit cooldown.

Interest groups & Telegram routing

Posts are classified at runtime and routed to per-group Telegram forum topics — the core “signal from noise” mechanism.

Classification

🎯 How a post matches a group

  • Account — post author contains any account in the group's accounts[] list.
  • Keyword — caption contains any keywords[] phrase (case-insensitive).
  • Hashtag — caption contains any hashtags[] tag.
  • Match reasons are stored (“account @mda_sc”, “keyword 'pronaf'”…) and shown in the explorer.
  • After detail-scraping a fuller caption, groups are re-matched — a keyword deep in the caption still counts.
  • Unmatched posts go to the main channel; matched posts only go to their groups' topics.
Telegram topics

💬 One forum topic per group

  • On startup, each group without telegramThreadId gets a topic via createForumTopic.
  • The group's color is mapped to the closest of Telegram's 8 icon colors; the ID is written back to groups.json.
  • Notifications include the screenshot, author, post link, match reasons and captured-comment count.
  • Created from the explorer too — adding a group in the dashboard provisions its topic.

The posting API

Publish images back to Instagram over HTTP — a full create-post UI automation driven by one synchronous request.

↔️ Sequence diagram — POST /post from client to permalink Open full size ↗

🔌 Endpoints

  • GET /health — status + cookie presence.
  • GET /status — cookie count + sessionid check.
  • POST /post — multipart image+caption, or JSON {imagePath, caption}.

🖱️ UI automation steps

  • “New post” → “Post” → upload file → Next (crop) → Next (filter) → caption → Share.
  • Debug screenshots saved at each failing step.
  • Success = extract permalink (/p/XXXX) and return it.

🔒 Safety

  • Bound to localhost:4030 — loopback only, never exposed publicly.
  • Images limited to 20 MB, jpg/png/webp/gif only.
  • Same cookies.json session as the watcher; CLI fallback: node poster.js img.jpg "caption".

Data & storage model

One SQLite database is the source of truth, shared between the watcher (writes) and the explorer (reads).

🗄️ posts.db — tables

Indexes on author, priority, timestamp, seen_at, comment shortcode/author. A custom fuzzy_match() SQL function (Unicode-normalize + Levenshtein ≤ 2) powers forgiving author/caption search.

The web explorer

A self-contained Express + vanilla-JS dashboard (dark theme, Docker-hosted on port 4180) over the same SQLite file — live at http://localhost:4180. Real screenshots of it on the next slide.

🖥️ UI features

  • Grid view — post cards with screenshot, author, caption preview, Reel/comments badges, group badges.
  • Filters — author (fuzzy), caption search (fuzzy), Reel vs photo, date range, group. Debounced, paginated (50/page).
  • Stats view — totals, priority count, reels, authors, last 24h/7d, comments, top authors, posts per day, group breakdown.
  • Post modal — full caption, comments with like counts, “Open on IG”, and manual group assignment checkboxes.
  • Groups admin (/settings) — create/rename/recolor/delete groups; add/remove accounts, keywords, hashtags. Creating a group also provisions its Telegram topic.

Deployment & scheduling

Everything runs on one Linux host; the watcher is a recurring cron job, the explorer is a Docker container.

Schedule

⏰ Cron job

  • Job IG Feed Watcher · schedule */5 * * * * · repeat ∞
  • Runs node watcher.js in the project dir; logs append to logs/.
  • Alternative documented: classic crontab or systemd timer.
Explorer

🐳 Docker container

  • Container ig-explorer · image node:22-slim + express only.
  • Ports 4180:4180 (LAN + Tailnet; keep it inside your network boundary).
  • Bind mounts: posts.db, screenshots/, groups.json, .env.config — stays in sync with the watcher.
  • Joined to the nginx-proxy-manager network; a systemd unit (ig-explorer.service) exists as an alternative.
Posting API

📤 Loopback service

  • node post-server.js → localhost:4030 (port via IG_POST_API_PORT).
  • Intentionally not exposed publicly — Tailnet/internal callers only.

⚙️ Configuration resolution

Telegram credentials resolve in order: .env.config (bot token + home channel) → process env (TG_BOT_TOKEN, TELEGRAM_HOME_CHANNEL). Watcher behavior lives in the CONFIG block of watcher.js (scroll count, page timeout, per-run cap, rate-limit cooldown, comment scraping toggles).

Operational notes & risks

Honest assessment of the fragile parts — and the mitigations already built in.

🛡️ Built-in mitigations

  • Rate limits: detail pages open only for matched / likely-truncated captions; ≥3 s between detail requests; a 429 pauses detail scraping for 30 min (cooldown persisted).
  • Anti-bot: real Chromium, realistic user-agent, AutomationControlled disabled, fonts/media aborted, popups dismissed.
  • Dedup & backlog control: every feed post is marked seen (even unprocessed), per-run cap of 10.
  • Failure alerts: fatal errors are sent to Telegram; hook and poster failures never kill the run.

⚠️ Known risks

  • Session expiry: Instagram rotates sessions — cookies must be re-exported every few weeks (login.js / DevTools / export-cookies.py).
  • Detection / ToS: scraping and UI automation violate Instagram's terms; an account ban is a real possibility.
  • Selector drift: parsing and the create-post flow depend on Instagram's DOM; debug dumps in the logs help re-fix selectors.
  • Explorer exposure: port 4180 is bound on all interfaces and has no authentication — it should only be reachable via LAN/Tailnet, ideally behind a proxy with auth.
  • DB growth: ~156 MB and growing; snapshot backups exist, no retention policy.
Recommendations: rotate the session proactively · back the explorer with an auth layer or private Tailnet ACL · add a screenshot/DB retention job · move the watcher to a more conservative cadence if Instagram rate-limits appear.
